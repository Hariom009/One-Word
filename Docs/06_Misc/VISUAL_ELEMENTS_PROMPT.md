---

You are a senior macOS product designer who also writes SwiftUI. **One Word** is a
word-of-the-day app for macOS with a WidgetKit widget. Its main competitor is **Lookup**
(Mac + iPhone), which leans heavily on visuals. Lookup's pictures and visual extras are part
of why people pay for it. Our job is to make One Word more **visual, engaging and
interactive** without losing what it is. Your job is to **give me options to choose from**.
Don't pick a winner and ship it.

## 1. Look at the competition

Open Lookup's Mac App Store and iPhone App Store pages (use the built-in browser) and study
the screenshots and description. Pull out **every visual or interactive device** it uses,
such as imagery per word, colour, charts, origin/etymology graphics, games and widgets. For
each one, note:

- **What job it does for the user.** Does it help them remember, make the app feel premium, give them a reason to come back, or make it shareable?
- **Whether we can do it under our constraints (§2).** If not, what version of it we can do.

One table, ≤15 rows. Don't copy Lookup's look. We take the *job* and answer it our way.

## 2. Hard constraints (an option that breaks one is out)

- **Offline, bundled, no network at runtime.** Everything ships in the app. No image APIs,
  no CDNs, no "fetch a photo per word".
- **No copyrighted or stock imagery.** We told Apple "no copyrighted dictionary or publisher
  material is included". Every asset has to be made by us, generated by code, CC0, or come
  with a licence we can show. ~12,000 words × a photo each also blows up the bundle size, so
  if you propose per-word art, say how it's produced and what it costs in MB.
- **The data we actually have per word:** `term`, `partOfSpeech`, `hindi`, `definition`,
  `example`, optional `sound`, plus related-word neighbours (embeddings) and the learned log.
  We have **no** etymology, syllables, IPA, frequency or images. If an option needs new data,
  say exactly which field, how it would be generated offline at build time (like
  `tools/gen_words/`), and that it means touching every book's JSON.
- **Premium lock.** A locked word shows only its headword (`WordDetail.locked`). Any visual
  that gives away the meaning (an illustration, a symbol, a related-word map) must not render
  on a locked word.
- **All five appearances + the doodle theme.** Each option has to look intentional in Light,
  Dark, Midnight (frosted, sans, pills, blue) and Umber (flat, serif, warm, brass). The
  doodle art and the Pulpen face are **app-only**. The widget can't draw them.
- **Standing design rule: "covers are the only coloured surface — the reading UI stays
  monochrome"** (`Wordbook.swift`). Some options can break this rule. If one does, say so
  plainly and argue for it.
- **The feeling stays calm, literary, word-first** (DESIGN_BRIEF §2). "Engaging" means
  delight and a reason to come back. It does not mean badges, confetti, and streak-shaming.
- **Accessibility:** every animation respects `accessibilityReduceMotion` (see
  `SentenceView` and `DictionaryPicker` for the pattern). Keep VoiceOver labels, contrast,
  and larger text working.
- **Performance:** the list holds 12,000 rows, so nothing per-row that's heavy.
- **Architecture:** Views stay dumb, and view models never import SwiftUI. `OneWord/Shared/` is
  wired by path in `project.pbxproj`, so don't add files there unless the widget truly needs
  them.

## 3. Generate options, per component

For each surface below, give **3 options** that take genuinely different positions (not three
recolours of the same idea). One should be safe, one bold, and one interactive. Each option
gets: a name, a one-line pitch, what it looks like in each appearance, the interaction, what
data it needs, how much work it is (S/M/L), and the risk.

1. **Word of the Day hero** (`WordDetail`, embedded in Home). The signature screen. Ideas to
   consider, not prescribe: the book's `mark` as a huge watermark behind the headword, an
   ink/handwriting entrance for the headword, a visual for part of speech, a per-word symbol
   or drawing, a "guess before you see it" reveal of the definition.
2. **A picture for the word.** This is Lookup's core move, so give it real thought. Compare at
   least: (a) a build-time SF Symbol pick per word (offline embedding match, with a
   confidence cut-off so it's blank rather than wrong); (b) a small set of drawn spot
   illustrations per *book* or per theme in the doodle style; (c) a typographic poster of the
   word, generated in code; (d) anything better you find. Say which one scales to 12k words
   honestly.
3. **Related words.** The current one is a collapsed `DisclosureGroup` list. Try a visual map
   or constellation of neighbours that you can click through.
4. **Progress / coming back.** `LearnedWords`, `MonthCalendar`, `LearnedSeal`, and the shelf
   could show growth visually. Ideas: a shelf that fills up, a heatmap, a word garden. Keep it calm.
5. **Interactive learning on the page.** Flip card, 3-choice "which meaning?", match the Hindi.
   Use only the words already in the selected book as distractors. Say how this relates to the
   existing Practice pane (`SentenceView`). Don't duplicate it.
6. **Widget** (small / medium / large). It's monochrome today, by design. Show what visual
   element, if any, earns a place there, and how it reads on a light *and* a dark wallpaper.
   Remember widget interactivity is App Intent buttons only.
7. **All Words list rows.** A visual cue per row (learned, part of speech, book), as long as it
   stays fast at 12k rows.

## 4. Make the options visible (this is the point)

I need to **see** them, not read about them. Build a throwaway **Visual Lab**:

- One DEBUG-only file, e.g. `OneWord/Views/VisualLab.swift`, wrapped in `#if DEBUG`, reached
  by a launch argument (the app already takes `--args demo` for screenshots). Use the same
  pattern, not a new menu.
- A gallery: rows = the components in §3, columns = the 3 options. Each one is rendered with
  the **real** `Theme`, real fonts, and real words (use "ephemeral", "trade",
  "lightheaded", an idiom, and a Cats & Dogs entry with a sound). A toolbar switches the
  appearance and the doodle theme, so I can flip all options through all five looks at once.
- Production code stays untouched. Lab views may copy small pieces of existing views. They
  must not refactor them. Deleting `VisualLab.swift` must remove the lab completely.
- Screenshot every component × option in Light and Midnight (and Umber where it matters)
  and put the images in the doc below.

Before you report back, run both gates from `CLAUDE.md` (the `xcodebuild` build + every
`tools/check_*.sh`). If one is red, show the output. Don't paper over it.
